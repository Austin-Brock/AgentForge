Can an AI agent learn the house rules?

A small test of one idea from a 2026 research paper: that an AI gets better at a job most reliably when each mistake teaches it one small, checked lesson, written in the right place.

The idea in plain words

Imagine a capable new hire at a company with unwritten rules. Nobody told them that “until Friday” means “until Thursday night”, so they keep getting things wrong. They are not short of skill. They are short of local knowledge.

AI models are in the same position when they work with something they have never seen. Retraining the model to teach it is slow and expensive. The cheaper way is to leave the model alone and give it a notebook that it reads before each job.

The paper, EMMA, is about how that notebook should be written. It has three sections:

  • Planning notes: how to split up a job and who should do which part.
  • Specialists: team members with extra instructions for one kind of work.
  • Skills: short how-to cards, pulled out only when they apply.

After each mistake a reviewer decides what kind of mistake it was. That decides which section the lesson belongs in. The reviewer may write exactly one small lesson. Then a rule-checker, which is ordinary code and not an AI, can refuse the lesson if it copies the answer to that one job, rewrites too much at once, or keeps changing the same place without success.

The paper's claim is that this careful process beats letting the AI rewrite its own notebook however it likes.

The experiment

We invented a small code library called kiln with six unwritten rules, so no AI could already know them. For example, its date ranges silently leave out the last day. We wrote 48 small programming tasks that can only be solved by knowing a rule. Each version practised on 18 of them, then was tested on the other 30 with its notebook frozen.

  • No notebook: the untrained agent. The baseline.
  • Careful (EMMA): one lesson per mistake, checked by the rule-checker.
  • Anything-goes: the reviewer may change anything, as much as it likes, with no checks.
  • Careful, revised reviewer: the careful version trained a second time with one change: the reviewer was told to name the tool involved and say exactly what it does. This was added after the first careful notebook came out vague. Both are shown so nothing is hidden.

What we found

  • The paper's claim did not hold up in this small test. The anything-goes version passed 76% of attempts on unseen tasks, twice the untrained agent's 38%, and well ahead of both careful versions.
  • The careful version as first built learned nothing useful: 37%, the same as having no notebook. Its lessons were too vague to act on. Told not to copy the task, its reviewer wrote things like "some date-range methods exclude a boundary" without naming the tool or the right boundary.
  • Telling the careful reviewer to be specific raised it to 53%. Where its notebook held a correct rule it passed nearly everything (date ranges 15 of 15, merging 11 of 15). Where it held a false rule it passed almost nothing (rates 0 of 15, shelf slots 1 of 15).
  • No version could tell a true lesson from a false one. The rule-checker checks a lesson's form, not whether it is right, and the reviewer wrote wrong lessons as confidently as correct ones.
  • The anything-goes version won mainly because it learned more from each mistake. It could write a how-to card, a planning note and a retry hint after a single failure, while the careful version was allowed one change. It also wrote down facts about the library in plain terms, which is what these tasks needed.
  • One rule-checker rule cost the careful versions most of their refusals: after two failed changes to the same section, a third is not allowed. With only three tries per task, that often meant a mistake taught nothing.
  • The anything-goes notebook is messier, as the paper predicts: 36 planning notes against 15, duplicates, and notes about one specific practice task. At this size the mess did not hurt. It might with hundreds of tasks, which is the setting the paper is about.
  • This does not show the paper is wrong. It was one made-up library, 18 practice tasks, a small AI model, and each version trained once. The paper's limits are designed for much longer training across varied work, where an unchecked notebook has room to bloat and contradict itself.

Skillledger-between-exclusive-bounds
Use when: when a task needs a date slice from kiln.Ledger
kiln.Ledger.between(start, end) returns entries with dates in the half-open interval [start, end): the start date is included and the end date is excluded. To cover a calendar month, use the first day of that month as start and the first day of the next month as end; for December, the next-month boundary is January 1 of the following year. Do not subtract a day from the end boundary. Example: between(2026-01-01, 2026-02-01) includes all January 1-31 entries.
Skillshelf-zero-based-indexing
Use when: when a task reads or writes kiln.Shelf slots
kiln.Shelf uses zero-based slot numbers. `get(0)` and `put(0, item)` refer to the first slot. `find(item)` returns `0` both for an item in the first slot and when the item is not found, so code using `find` must not treat `0` as a guaranteed hit or as a guaranteed miss without additional handling.
Skillshelf-first-slot-access
Use when: when a task needs the item in the first logical slot of a kiln.Shelf
kiln.Shelf slot numbering is zero-based, and the first slot is slot 0. Use shelf.get(0) to read that slot; it returns the item stored there or None if the slot is empty. Do not search for the first non-empty slot unless the task explicitly asks for it.
Skillkiln-fee-per-thousand
Use when: when a task uses kiln.fee for percentage-like calculations
kiln.fee(amount, rate) computes floor(amount * rate / 1000) and returns an int. Pass the rate exactly as kiln.fee expects; do not convert ordinary percent values into 0–100 percentages unless the task explicitly says to do so. Example: rate 1000 on 100 gives 100, and rate 100 on 100 gives 10.
Skillkiln-merge-inner-only
Use when: when a task combines two lists of keyed records with the merge function
The merge function only works correctly when both input lists are already sorted by key. It returns a key-sorted list and combines equal keys by summing their quantities; it does not rescue unsorted input on either side. Before calling it, convert any mapping or other unordered source into a key-sorted list of (key, qty) records, then use the merge result directly without re-sorting.
Skillledger-entry-amount-direct
Use when: when a task reads monetary amounts from kiln.Ledger entries
kiln.Ledger entries expose the stored amount directly in the third tuple field; that value is the ledger amount itself and should be summed as-is. If the task asks for dollars, convert the final total to dollars before returning, rather than changing the month filtering logic. Example: sum the matching entry amounts first, then apply the task’s required unit conversion to the total only.

Limits of this test

  • It is one small made-up library and 30 test tasks, with each version trained once. The paper used three public benchmarks and five AI models. This is a test of the idea, not a reproduction of the paper's numbers.
  • Results vary from run to run, which is why every test task was tried 3 times. Small gaps between versions should not be read as real differences.
  • The anything-goes version is our own design, not one of the paper's comparison systems.
  • Workers used OpenAI's gpt-5.4-nano and the reviewer used gpt-5.4-mini. The paper uses one model for every role.
